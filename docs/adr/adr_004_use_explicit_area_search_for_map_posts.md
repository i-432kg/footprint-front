# ADR: マップ画面の投稿取得を明示的なエリア再検索方式にする

## ステータス
Proposed

## 背景
現在のマップ画面では、Leaflet の表示範囲に基づいて投稿を取得している。

`src/components/post/PostMap.vue` では、初期表示時に現在地またはデフォルト位置を表示した後、地図の bounds を使って `/posts/search/map` を呼び出している。

また、地図の `moveend` イベントでも `fetchPosts()` を呼び出しているため、次の操作で都度 API が実行される。

- 地図の初期表示
- 現在地取得後の表示位置更新
- 地図の移動
- ズームイン / ズームアウト

この方式は表示範囲と投稿一覧が常に同期しやすい一方で、地図操作のたびに API 呼び出しとマーカー再描画が発生する。

さらに、ズーム操作時に Leaflet の `Marker._animateZoom()` で `this._map` が `null` になり、`_latLngToNewLayerPoint()` を読めずエラーになる事象が確認されている。
原因として、ズームアニメーション中または連続操作中に、非同期 API レスポンスを契機として既存マーカーを全削除・再作成していることが疑われる。

## 問題
- 地図の移動やズームのたびに API が実行され、呼び出し頻度が高い
- 連続ズームやパン操作時に複数の API リクエストが重なりやすい
- 古い API レスポンスが後から返ってきた場合、現在の地図状態と異なるマーカー描画が起きうる
- API レスポンス後に全マーカー削除・再作成を行うため、Leaflet のズームアニメーションと競合しやすい
- ユーザーにとって、どのタイミングで投稿一覧が更新されるのか分かりづらい

## 決定
マップ画面の投稿取得方式を、地図操作ごとの自動再取得から、ユーザーが明示的に実行するエリア再検索方式へ変更する。

具体的には、初期表示時のみ現在の bounds で投稿を取得する。
その後、地図の移動やズームで表示範囲が変わっても即座には API を呼び出さない。

表示範囲が変更された場合は、地図上に「このエリアで再検索」ボタンを表示する。
ユーザーがこのボタンを押した時だけ、現在の bounds を使って `/posts/search/map` を呼び出す。

## 設計方針

### 1. 初期表示時は自動取得する
マップ画面を開いた直後は、現在地またはデフォルト位置を表示したうえで、初期 bounds に基づいて投稿を取得する。

これにより、画面を開いた時点で投稿マーカーが表示される状態は維持する。

### 2. `moveend` では API を呼び出さない
`moveend` は地図移動だけでなくズーム完了時にも発火する。

そのため、`moveend` の役割は API 呼び出しではなく「表示範囲が変更された」という状態更新に限定する。

想定する状態:

- `hasMoved`: 表示範囲変更後、まだ再検索していないかどうか

### 3. 「このエリアで再検索」ボタンから API を呼び出す
表示範囲が変更された場合、地図上に再検索ボタンを表示する。

ユーザーが押下した時のみ、現在の bounds で投稿を取得し、マーカーを更新する。

これにより、API 呼び出し頻度をユーザー操作に紐づけて制御できる。

### 4. 古い API レスポンスを破棄する
明示的再検索方式にしても、連続クリックや初期取得との競合は起こりうる。

そのため、`fetchPosts()` には request id を導入し、最新リクエスト以外のレスポンスは描画に反映しない。

### 5. Leaflet インスタンスは Vue の深いリアクティブ化を避ける
Leaflet の `Map`、`Marker`、`Control` は内部状態を持つ外部クラスであり、Vue の通常 `ref` による深い Proxy 化と相性が悪い。

マップ関連インスタンスは `shallowRef` または `markRaw` を使い、Leaflet 内部状態を Vue のリアクティブシステムに巻き込まない。

### 6. マーカー更新はズーム操作と競合しないタイミングで行う
再検索ボタン押下時にのみマーカー更新を行うことで、ズームアニメーション中の削除・再作成を避けやすくする。

必要に応じて、ズーム中フラグを導入し、ズーム完了後にマーカーを更新する。

## 選択肢

### 案1: 現状のまま `moveend` ごとに自動取得する
不採用。

理由:

- API 呼び出し頻度が高い
- 連続操作時にリクエストが重なりやすい
- マーカー全削除・再作成が Leaflet のズームアニメーションと競合しやすい
- 今回確認されたズーム操作時エラーの発生条件を残しやすい

### 案2: `moveend` 後に debounce して自動取得する
不採用。

理由:

- 実装は軽いが、地図操作に応じて API が自動実行される構造は残る
- 操作が多い場合、API 呼び出しを完全には抑制できない
- ユーザーにとって更新タイミングがやや不透明である

### 案3: 一定距離以上の移動またはズーム差が大きい場合のみ取得する
不採用。

理由:

- API 呼び出し頻度は抑えられるが、どの操作で更新されるかユーザーに分かりづらい
- 距離やズーム差の閾値設計が必要になる
- 画面上の投稿がいつ更新されるかが暗黙的になる

### 案4: 表示範囲より広めに取得してクライアント側キャッシュする
不採用。

理由:

- UX はよいが、キャッシュ範囲管理や投稿数上限の設計が必要
- 初期対応としては実装量が大きい
- バックエンド API の返却件数や地理検索仕様も含めた検討が必要になる

### 案5: 明示的な「このエリアで再検索」方式にする
採用。

理由:

- API 呼び出し頻度を明確に抑制できる
- ユーザーが投稿一覧更新のタイミングを理解しやすい
- ズームやパン操作中にマーカー再描画が走りにくくなる
- 既存 API を維持したまま実装できる
- Leaflet のズーム操作時エラーの発生条件を減らせる

## 実装手順
1. `PostMap.vue` の `moveend` で `fetchPosts()` を直接呼ばないようにする
2. `moveend` では `hasMoved` のような状態を `true` にする
3. `hasMoved` が `true` のとき、地図上に「このエリアで再検索」ボタンを表示する
4. ボタン押下時に現在の bounds で `fetchPosts()` を実行する
5. 投稿取得が成功したら `hasMoved` を `false` に戻す
6. `fetchPosts()` に request id を導入し、古いレスポンスを破棄する
7. Leaflet の `map`、`markers`、`zoomControl` を `shallowRef` または `markRaw` で扱う
8. ズーム連続操作、パン操作、再検索ボタン連打でエラーが発生しないことを確認する

## 期待する効果
- 地図操作ごとの API 呼び出しを抑制できる
- 投稿マーカーの更新タイミングがユーザーに明確になる
- ズームアニメーション中のマーカー削除・再作成を避けやすくなる
- Leaflet のズーム操作時エラーの発生条件を減らせる
- 将来的にキャッシュやクラスタリングへ拡張しやすくなる
